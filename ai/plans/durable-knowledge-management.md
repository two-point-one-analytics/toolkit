# Knowledge System Bootstrap

## Goal

Stand up a working knowledge system where the input is not a blank slate: there is already **a substantial body of notes and organizational documentation** that needs to become retrievable context rather than material sitting inertly on disk.

Three things have to be true when this is done:

1. **The existing corpus is processed** — classified, placed, and reachable by an agent that does not already know what it is looking for.
2. **New knowledge has a path in** — extraction skills that read a source artifact and propose additions rather than writing silently.
3. **It stays true** — a reconciliation pass that consolidates overlap, detects conflicts, and surfaces uncertainty for review instead of editing on its own authority.

## Scope Boundary

This plan is about **the knowledge system**, not the tooling that operates it.

Installing and verifying the skills, agents, and instruction file is the repository README's job, and it should land first — characterizing a corpus is itself work you want the agent tooling for. That installation closes when the skills run; this plan closes when the knowledge is usable.

The distinction is worth holding: the install delivers a toolbox, this delivers a library. Finish the install and stop, and you have working skills with nothing useful to point them at.

## Premises

- **The corpus is the distinguishing feature.** Most knowledge-system designs assume you accumulate from zero. Here a substantial body already exists, which inverts the first problem: the hard part is classification and placement, not capture.
- **Volume shifts the bottleneck from capture to reconciliation.** The work environment has AI tooling already connected to email, chat, meetings, and other systems, so intake will be high and partly automated. Checking, pruning, and connecting is what becomes constraining.
- **Anything built here must survive being copied without its surrounding environment**, since it arrives by hand across a deliberate gap.

## Decisions

Carried forward so they are not re-litigated.

- **Memory categories are distinguished by termination condition**, not lifespan or topic. A note leaves when acted on, a plan when the work completes, a KB entry never — it gets revised. This is the test for any proposed new category: if its entries would leave for the same reason as an existing category's, it is not a new category.
- **The gap is a missing edge, not a missing category.** Work-memory and world-model are both covered; what does not exist is the promotion path between them. This is why the answer is extraction skills rather than a fifth store.
- **Three states of context availability** govern placement: in context, aware-but-not-loaded, and invisible-without-search. **State 3 is only reachable via a pointer from state 1 or 2** — a searchable pool with no retrieval instruction is functionally absent however well written. This is the single rule most likely to be violated when processing a large corpus quickly.
- **A slot in the index is the scarce resource, not disk space.** Admitting something to the always-read map should be high-friction; growth pressure belongs in the searchable pool.
- **Extraction proposes; a human approves.** Skills scrape and suggest, they do not write into the KB directly.
- **Reconciliation surfaces uncertainty rather than resolving it.** Output is a review list, not silent edits. Consolidation it can perform confidently is still recorded, not invisible.
- **The verification property is a prerequisite, not a feature.** Without a record of when a claim was last confirmed and against what, reconciliation cannot distinguish stale from settled and re-examines everything every pass.
- **The review queue is itself memory** and needs a home and a termination condition. It is notes-shaped — open items that die when resolved — but generated by an agent rather than a person, which is why it may not belong in the same file.
- **Autonomous consolidation is the highest-risk operation in the system**, because it edits the layer everything else trusts. Provenance on every agent edit and a way to reverse one are requirements.
- **A temporal activity log was considered and rejected.** Its appeal was capturing *why* things changed — decision provenance, not chronology — and that is what extraction addresses. Calendar, email, chat, and git already hold the events.
- **Work-task tracking stays in the external system.** It owns status; the repo owns context; neither restates the other's fields.

## Success Criteria

- [ ] **Corpus characterized** — what exists, where it lives, in what formats, roughly how much, and which parts are worth processing at all (Q1).
- [ ] **Placement decided** — which material becomes always-loaded instruction, which earns an index slot, and which lands in the searchable pool. Applied consistently rather than per-file.
- [ ] **Retrieval protocol established** — the pointer from state 1 or 2 into the searchable pool, without which the pool is invisible.
- [ ] **The existing corpus processed into that structure**, not merely copied into it.
- [ ] KB entries carry a **verification property** — when last confirmed, and against what (Q2).
- [ ] One or more **extraction skills** read a source artifact and propose additions rather than writing directly (Q4).
- [ ] A **reconciliation pass** consolidates overlap, detects conflicts, and proposes connections.
- [ ] It emits a **review queue** with a defined home and termination condition (Q3).
- [ ] Every agent-made edit carries **provenance and is reversible** (Q5).
- [ ] Merged with the plan files already on the work system, and that merged plan supersedes this one.

## Next Action

**Characterize the corpus before designing anything for it** (Q1).

Every downstream decision — placement, whether extraction is one skill or several, whether reconciliation needs to run on a schedule or on demand — depends on what is actually there. Designing first and discovering second is how a structure ends up fitting the imagined corpus rather than the real one.

Install the skills first (see the repository README) so the tooling is available to do the survey with.

## Open Questions

### Q1. What is the corpus, concretely?

Volume, formats, locations, and how much is worth processing. Personal notes and company documentation are different problems: the notes are yours to restructure freely, while company documentation may be authoritative elsewhere and should be referenced rather than copied — duplicating it creates exactly the drift the memory model warns about.

The sub-question that matters most: **which parts are canonical elsewhere?** Anything with an owner and a live source belongs behind a pointer, not in a copy.

### Q2. What shape does the verification property take?

Frontmatter field per file, an inline marker per claim, or a sidecar record. Whole-file granularity is cheap and matches a flat-file convention but is coarse — one stale claim marks a whole file suspect. Per-claim is precise and expensive to maintain. The choice determines what reconciliation can actually check.

### Q3. Does the review queue share the notes file, or get its own home?

Sharing keeps one destination and reuses the existing note skills. Separating keeps agent-generated volume from drowning hand-written open loops, which matters more as automated intake scales. Leaning separate, for that reason.

### Q4. Is extraction new skills, or an evolution of the existing capture family?

`capture` already exists and writes to a repo's searchable pool. Extraction as specified reads *finished* artifacts and proposes KB insertions — structurally the same shape as the unbuilt `promote`, whose design is preserved in `specs/promote.md`. Building one may settle the other by precedent rather than by decision.

(A sibling skill, `ingest`, wrote meeting summaries into the same pool but was not ported — it depended on a meeting-notes MCP server that does not exist here. Worth knowing the shape existed if an equivalent source needs wiring up.)

### Q5. How much may reconciliation change without approval?

A spectrum from propose-only, through auto-merge of exact duplicates, to autonomous restructuring. The answer likely varies by operation type rather than being one global setting.
